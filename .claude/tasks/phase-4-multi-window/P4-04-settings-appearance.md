# P4-04 · Settings ▸ Appearance

**Phase:** 4 · **Status:** ✅ · **DEV_TASKS:** U12 · **Depends on:** P4-03

## Goal
The Appearance category: theme selection (live) + related display prefs.

## Built (`crates/strata-freya/src/apps/settings/views/theme.rs`)
`ThemePane` replaced P4-03's `Pane::not_built(..)` placeholder. It only ever writes
`SettingsCtx::draft`'s `theme` / `sync_os` — the live-preview mechanism was already built and
tested, so nothing here touches the `ThemePreview` slot or `write_config`; the window root
mirrors the draft's theme half and the footer's Apply persists. Pinned by
`theme::tests::a_preview_outranks_the_committed_theme_until_it_is_dropped`.

- **Sync with OS** — title + one-line description + Freya's `Switch`, writing `sync_os`.
- **The theme grid** — every `ThemesCtx` entry, two cards to a row (`chunks(2)` of `flex(1.)`
  cards; a short last row is padded so its cards keep the width they'd have in a full one — Freya
  lays out in flex, there is no CSS grid). Each card: a **miniature of the app in that theme**,
  then its name, a `Badge::tag` source badge (BUNDLED / USER, from `ThemeEntry::source`) and a
  tick when selected. Picking one writes `theme` **and clears `sync_os`** — the canvas does the
  same, because leaving it on would show a tick the OS is free to move.
- While `sync_os` is on the grid is dimmed (.55) and `interactive(false)` — the canvas's
  `pointer-events: none` — under the hint "Following your system appearance…". Deliberately inert
  rather than absent: it is still the only thing on the pane that answers *which* theme is in use.

## Corrections / decisions this task carried

### The swatches are the previewed theme's data, not a token
A card's thumbnail is painted from four slots of **the theme it stands for** — `background`,
`surface_secondary`, `border`, `primary`. Verified against the canvas: those four resolve to
exactly the `pal` quadruples `strata-theme.js` hardcodes for Midnight and Daylight. So a user
theme dropped in the themes dir gets a true preview with nothing authored per theme, and there is
no per-theme swatch list to keep in step. Only the card's *frame* (surface, ring, badge, tick) is
the `settings` component theme, because that belongs to this window. `theme::pc` became
`pub(crate)` for it: these are colours of a theme that is **not** installed, so they can't come
off a resolved `Theme`.

### The tick follows the effective theme, not the stored id
While Sync-with-OS is on, `draft.theme` is not what any window is wearing. The pane resolves
through `ThemeSel::effective` — the same pure function `use_strata_theme` derives with — so the
tick can never disagree with what is on screen. The OS-appearance read is short-circuited behind
`sync_os`, so the pane only subscribes to `Platform.preferred_theme` while syncing.

### Apply is a per-field diff (the gap P4-03 flagged)
Making the draft editable armed P4-03's known gap: `apply` wrote the *whole* `Settings`, so a
setting another window committed meanwhile was reverted. Settled with the **per-field diff**:

- `Settings::merge_onto(&self /* draft */, base, live)` in `strata-core::config`, generated by
  `settings_merge!` from one field list. The list is checked by the compiler — the generated
  `let Settings { … } = self` pattern names every field, so **adding a setting without listing it
  is a build error** (verified: removing one fails with "pattern requires `..` due to inaccessible
  fields", pointing at both the pattern and the invocation) rather than a field the window can
  edit and never commit. That is the whole reason it is a macro and not a hand-written sequence.
- `SettingsCtx` gained `seed: State<Settings>` — written once at mount, never again — as the diff
  base. Three unit tests pin it: the other window's field survives, a field the draft *did* change
  wins over a concurrent write (last Apply wins), and an untouched draft commits nothing.
- **`use_dirty` → `dirty()`.** The right predicate is `draft != seed` ("has the user changed
  anything"), not `draft != committed`: the old one lit Apply up for a change *another* window
  made, and Apply — now a merge — would then commit nothing. It reads no config state, so it
  stopped being a hook and the footer lost its config subscription entirely.

### Theme tokens
Seven new `settings` fields, all authored as references in both theme files: `card_background`,
`card_border_fill`, `card_hover_border_fill`, `card_divider_fill`, `selected_color`,
`badge_builtin_color`, `badge_user_color`. `selected_color` is **one** field for the ring *and*
the tick — they are one meaning, and two fields would be the same colour named twice.

Two AGENTS §2 cleanups fell out of first-using controls this pane needed:

- The hover ring's tone (`#4e5866` / `#aeb3bd`) was a repeated `specific` on
  `checkbox.hover_border_fill`. Second use ⇒ promoted to a `border_hover` palette slot, both
  referencing it (no visual change) — the same move P4-03 made for `accent_selection`.
- **`Switch` is first used here**, and was unauthored: Freya's default is 48×28, the canvas 34×19
  with a 15px knob. `switch_layout` is now authored in both themes to the canvas. Its off-state
  track was two bare `specific`s, and midnight's had drifted off the canvas (`active` instead of
  `--c-border3`); both now reference `border_overlay`.

### Fork addition
`Toggled` is re-exported from `freya-core`'s prelude beside `AccessibilityRole`. The cards are
`AccessibilityRole::RadioButton` with their selected state announced, and `a11y_builder` already
exposed the raw accesskit node — only the *type* was unreachable, which would otherwise have meant
an app-side `accesskit` dependency version-locked to Freya's (AGENTS §6: fix it in the fork).

### Known latent: the preview path has the same stale-draft problem Apply just lost
`SettingsCtx::sync_preview` mirrors the draft's theme half **unconditionally**, and the preview
outranks the committed settings in every window. So an untouched draft *pins* the theme as it was
when Settings opened: if another surface commits `settings.theme` while Settings is open, no window
shows it until Settings closes and the slot is dropped. Exactly the stale-draft-wins shape the
per-field merge removed from the commit path, still present on the preview path.

**Unreachable today** — the Settings window is the only writer of `theme` — and deliberately left,
because the fix (teach `sync_preview` the seed, so an untouched theme half publishes nothing)
changes what the preview means and wants doing alongside whatever second surface makes it
reachable. Whoever adds that surface owns it.

### Traps worth keeping
- `Switch`'s `on_press` does **not** stop propagation, so a pressable **ancestor** of the switch
  takes the same click and toggles twice. The row is therefore two siblings: the label block takes
  the press, the switch stays independently focusable.
- **The ring took three goes.** A card with edge-to-edge content needs an *inner* border **plus**
  content inset by the ring width **plus** an inner radius of `CARD_RADIUS - width` on the inset
  child (and a clip on it, for its own full-width children). `BorderAlignment::Outer` is not the
  shortcut it looks like: it draws outside the bounds the clip rounds to, so only the corner arcs
  survive.
- **`Size::flex` does nothing without `content(Content::Flex)` on the parent.** Three rows here
  were missing it; the visible symptom was a control pushed off the pane, but the quieter one was
  a `percent`-sized child measured against the wrong box.
- **A disabled control gates its *handlers*, it does not go `interactive(false)`.** Freya's own
  components are the reference: `Switch` wraps only `on_press` / `on_pointer_down` in
  `.maybe(enabled, …)` and leaves `on_pointer_enter` / `on_pointer_leave` registered
  unconditionally, so hover state stays truthful while disabled. `interactive(false)` kills *all*
  pointer events including `pointer_leave`, which leaves a hovered card's flag stuck true — the
  ring then comes back stale as soon as the cards go live again. The grid tracks hover always and
  only *dresses* it when live. (The fork's three `interactive(false)` uses are pass-through
  overlays — tooltip, drag ghost, docking — never a disabled control.) A `use_side_effect` that
  clears the stale flag afterwards is treating the symptom; it also has to be
  `use_side_effect_with_deps`, since a bare one reruns only on reactive reads *inside* it and a
  captured `bool` is not one.
